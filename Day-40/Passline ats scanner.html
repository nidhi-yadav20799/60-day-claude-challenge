How this was built

Passline is one HTML file: a scanner-themed interface driving a single structured call to Claude. No frameworks, no backend — the browser calls the Claude API directly and renders whatever comes back.

System prompt design

The model is scoped narrowly to one job: grade a resume against ATS parsing conventions and, if given one, a job description. It's instructed to return only raw JSON — no markdown fences, no commentary — matching a fixed schema (score, verdict, section scores, an issues list, keyword match, prioritized fixes).

Two constraints do most of the work:

  • Verbatim excerpts. Every flagged issue must include an exact substring of the submitted resume, short enough to be unambiguous. That's what lets the browser find and highlight the exact phrase in your resume without any NLP on the client side — the model does the locating, the browser just wraps a <span> around a string match.
  • A valid_input escape hatch. If the pasted text isn't a resume (empty, gibberish from a failed file read, unrelated text), the model sets valid_input: false and explains why instead of forcing a score onto nonsense input.

It's also told never to invent resume content that isn't there, to give a real (sometimes unflattering) score rather than a polite average, and to still produce a useful general ATS review when no job description is provided — just without keyword matching.

Why the UI looks like this

Every visual idea traces back to what an ATS actually does: it scans a document and gates it through a pass/fail check. That's why the report opens with a literal scanning-laser animation over a document silhouette, why the score reads as a "clearance" dial with tick-style progress rather than a generic donut chart, and why the verdict states read CLEARED / FLAGGED / BLOCKED instead of a plain pass/fail label.

The resume markup view renders on light "paper" against the dark shell — deliberately looking like a printed page under a reviewer's pen, with color-coded underlines standing in for a recruiter's red pen and a coach's highlighter.

Left/right split mirrors the mental model: feed the scanner on the left, read the printout on the right. The intake column stays pinned so you can tweak the résumé and re-run without losing your place in the report.

Extending this

  • Real file parsing. Right now only .txt is read client-side (no external libraries were used, by design). Drop in pdf.js or mammoth.js to extract text from real PDF/DOCX uploads instead of asking users to paste.
  • Tools. Give the model a web-search tool to pull live examples of how a specific ATS (Workday, Greenhouse, Taleo) parses tables and columns, or a retrieval tool over a curated keyword/synonym database per industry.
  • Memory. Store each scan (score + issues) client-side or in a small backend so a user can re-scan after edits and see a before/after delta — "your clearance score went from 58 to 81."
  • Multi-step flow. Turn the single call into a pipeline: one call to extract structured resume sections, a second to score against the JD, a third to draft rewritten bullet lines for each flagged issue — then let the user accept fixes inline.
  • Follow-up chat. Add a lightweight chat thread anchored to the report so a user can ask "why did this bullet get flagged?" or "rewrite this line for me" without re-running the whole scan.
